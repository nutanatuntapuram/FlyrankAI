# Task API

A simple CRUD (Create, Read, Update, Delete) REST API for managing tasks, built with **Python** and **FastAPI**.

This project was built as a learning exercise to understand the fundamentals of building, testing, documenting, and publishing a backend API.

## Features

- Full CRUD support for tasks (create, list, get one, update, delete)
- Input validation with proper HTTP status codes (`200`, `201`, `400`, `404`, `204`)
- Interactive API documentation via Swagger UI (auto-generated by FastAPI)
- **Persistent storage with PostgreSQL, running in Docker** — data survives both app and container restarts
- **Repository pattern architecture** — storage backend is fully swappable; the app previously ran on SQLite and now runs on Postgres with no changes to any route or business logic

## Architecture: the repository pattern

This project separates **routes** (HTTP handling, validation, status codes) from **storage** (how/where data is actually saved), using a repository interface:

```
routes (main.py)
      ↓ calls
TaskRepository interface (repository.py)
      ↓ implemented by
SQLiteTaskRepository   OR   PostgresTaskRepository
```

Each repository (`sqlite_repository.py`, `postgres_repository.py`) implements the exact same five methods: `get_all`, `get_by_id`, `create`, `update`, `delete`. Because routes only ever call `repo.<method>()` and never touch SQL directly, **switching from SQLite to Postgres required changing only two lines in `main.py`** (the import and the repository instantiation) — no route, no validation logic, and no status-code behavior changed. This is documented honestly here rather than just claimed: the diff for that switch was a two-line change.

## Database

This project uses **PostgreSQL**, running in a **Docker container**, as its primary datastore. (An earlier version of this project used SQLite — that repository implementation, `sqlite_repository.py`, is still included in the codebase as a working example of the same interface, but is not the one currently wired into `main.py`.)

**Why Postgres + Docker?**
- Postgres is a real, production-grade relational database — the same technology used by most real backend services
- Running it in Docker avoids installing Postgres directly onto the host machine — the entire database is disposable and reproducible via a single config file (`docker-compose.yml`)
- A **named Docker volume** keeps the actual data on disk, independent of the container's lifecycle — so deleting/recreating the container does not delete the data

**Where the data lives:**
- Inside the `db` container, Postgres stores its files at `/var/lib/postgresql/data`
- That path is mounted to a **named Docker volume** (`postgres-data`), defined in `docker-compose.yml` — this is what makes the data survive container restarts and recreation
- Connection details are read from a `.env` file (see below) — never hardcoded

**Schema** (`init.sql`, automatically applied by Postgres on first container startup):

```sql
CREATE TABLE IF NOT EXISTS tasks (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    done BOOLEAN NOT NULL DEFAULT FALSE
);
```

**Example query used in this project** (fetching a single task by id):
```sql
SELECT * FROM tasks WHERE id = %s;
```

## Environment variables

Connection details are stored in a `.env` file, which is **gitignored** and never committed. A `.env.example` is committed instead, showing the required shape without real credentials:

```
DATABASE_URL=postgresql://username:password@localhost:5432/taskdb
```

To run this project, copy `.env.example` to `.env` and fill in real values (or use the defaults already set in `docker-compose.yml` for local development).

## Running with Docker Compose (recommended)

This starts **both** the Postgres database and the API together, with one command:

```bash
docker compose up
```

What this does:
- Builds the API image from the `Dockerfile`
- Starts a Postgres container with a persistent named volume
- Automatically runs `init.sql` to create the `tasks` table on first startup
- Waits for Postgres to report healthy before starting the API (via a healthcheck)
- Exposes the API at `http://localhost:8000`

To stop everything:
```bash
docker compose down
```
(This stops and removes the containers, but **not** the volume — your data is preserved for the next `docker compose up`.)

## Requirements

- Docker Desktop (recommended path — see below)
- OR Python 3.10+ and a local/remote Postgres instance (manual path)

## Installation & Running (Docker — recommended)

```bash
git clone <this-repo-url>
cd crud-api
cp .env.example .env
docker compose up
```

The API will be running at: `http://localhost:8000`
Interactive Swagger docs: `http://localhost:8000/docs`

## Installation & Running (manual, without Docker Compose)

```bash
python3 -m venv venv
venv\Scripts\activate          # Windows
# source venv/bin/activate     # macOS/Linux
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

This requires a Postgres instance already running and reachable via the `DATABASE_URL` in your `.env` file.

## Endpoints

| Method | Endpoint         | Description                          | Success Status | Error Status |
|--------|------------------|---------------------------------------|-----------------|---------------|
| GET    | `/`              | Returns basic API info                | 200             | —             |
| GET    | `/health`        | Health check — confirms server is up  | 200             | —             |
| GET    | `/tasks`         | List all tasks                        | 200             | —             |
| GET    | `/tasks/{id}`    | Get a single task by id               | 200             | 404 if not found |
| POST   | `/tasks`         | Create a new task (`title` required)  | 201             | 400 if title missing/empty |
| PUT    | `/tasks/{id}`    | Update a task's `title` and/or `done` | 200             | 400 (bad body) / 404 (not found) |
| DELETE | `/tasks/{id}`    | Delete a task                         | 204 (no body)   | 404 if not found |

## Proving persistence

Persistence was verified by:

1. Starting the stack: `docker compose up`
2. Creating a task via `POST /tasks`
3. Confirming it appeared in `GET /tasks`
4. Stopping everything: `docker compose down` (this removes the containers, but not the named volume)
5. Restarting: `docker compose up`
6. Running `GET /tasks` again — the previously created task was still present, confirming the data survived a full app + container restart, backed by the Postgres named volume rather than any in-memory or container-local state

## Notes

- This project evolved through three storage stages: in-memory list → SQLite file → PostgreSQL in Docker. Each stage kept the same API behavior; only the storage layer changed.
- The repository pattern (see `repository.py`) is what made the final swap to Postgres a two-line change in `main.py`, with zero changes to routes or validation logic — this is documented honestly above, not just claimed.
- Built as part of a step-by-step backend fundamentals exercise: hello world → routing → CRUD → validation → docs → publishing → SQL persistence → Docker + Postgres + repository pattern.
